# ADR-0002: Chunking Strategy — Small-to-Big

**Статус:** accepted
**Дата:** 2026-05-29
**Автор:** Александр Мельник

---

## Контекст

Документы нужно разбить на чанки для индексации. Чанк — единица поиска. Проблема: маленькие чанки дают точный поиск, но LLM получает бессмысленные фрагменты без контекста ("orphan chunk problem"). Большие чанки дают контекст, но embedding становится размытым — в 512 токенах много "шума", поиск менее точный.

Приоритет системы: recall первичен.

## Рассматриваемые варианты

### Вариант 1: Flat chunks (фиксированный размер)

Нарезка по 512 токенов с overlap 64.

**Как работает:** документ делится механически, без учёта структуры.
**Плюсы:**
- Простейшая реализация
- Предсказуемый размер индекса
**Минусы:**
- Orphan chunk problem: чанк вырван из контекста, LLM получает бессмысленный фрагмент
- Режет посередине мысли, абзаца, предложения
**Риски:**
- Качество ответов LLM низкое на документах с нарративной структурой

### Вариант 2: Sentence Window Retrieval

Нарезка по предложениям, при retrieval возвращается окно ±N предложений.

**Как работает:** ищем по маленьким единицам (предложениям), расширяем до окна соседей.
**Плюсы:**
- Очень точный поиск
- Нет LLM при индексации
**Минусы:**
- Размер окна — гиперпараметр, ответ может выходить за границу
- Плохо работает на PDF с bullets и таблицами
**Риски:**
- Для смешанного корпуса (статьи разной длины) ненадёжно

### Вариант 3: Parent Document Retrieval

Большие секции (parent) + маленькие чанки (child). Ищем по child, возвращаем parent целиком.

**Как работает:** parent = полная секция документа, child = её фрагменты.
**Плюсы:**
- LLM получает полный контекст секции
- Нет LLM при индексации
**Минусы:**
- Размер parent не контролируется (секция может быть 200 или 3000 токенов)
- Непредсказуемый token budget для LLM
**Риски:**
- На смешанном корпусе плохо работает из-за неоднородного размера секций

### Вариант 4: Small-to-Big (иерархические чанки)

Два уровня с контролируемыми размерами: L1 (~128 токенов, поиск) + L2 (~512 токенов, контекст).

**Как работает:** L2 нарезается из секций документа, L1 — из L2. Ищем по L1, expand к L2 для LLM.
**Плюсы:**
- Точный поиск (маленькие L1) + богатый контекст (предсказуемые L2 по 512 токенов)
- Предсказуемый token budget: всегда ~512 токенов на источник
- Нет LLM при индексации
- Работает на смешанном корпусе (заметки 200 слов + статьи 20 страниц)
**Минусы:**
- Сложнее схема: две роли чанков, parent_chunk_id связь
- Overlap на L2 создаёт дублирование контента
- Размеры 512/128 — гиперпараметры, могут потребовать тюнинга
**Риски:**
- Если L2 overlap слишком большой — дублирование в ответах LLM

## Решение

Выбрал **Вариант 4: Small-to-Big**.

Корпус смешанный (короткие заметки и длинные PDF), поэтому Parent Document Retrieval с его непредсказуемым размером секций не подходит. Small-to-Big решает orphan chunk problem (LLM получает 512 токенов связного текста), даёт точный поиск (128 токенов — мало шума в embedding), и предсказуемо потребляет токены LLM. Sentence Window отпал из-за ненадёжности на нарративных текстах разной структуры.

Стартовые параметры: L2 = 512 токенов (overlap 64), L1 = 128 токенов (без overlap). Пересмотреть после первичной индексации.

## Последствия

**Придётся:**
- Реализовать `SmallToBigChunker` с двухуровневой нарезкой
- Хранить `chunk_role` ('parent' | 'leaf') и `parent_chunk_id` в схеме
- При retrieval делать Expand to L2 через JOIN

**Стало проще:**
- LLM всегда получает контекст фиксированного размера (~512 токенов)
- Orphan chunk problem решена структурно, не промптингом
- Путь к Contextual Enrichment (ADR-будущее): добавить LLM-prefix на L1 при индексации без изменения retrieval

**Стало невозможным:**
- Простая flat-индексация без связей между чанками
