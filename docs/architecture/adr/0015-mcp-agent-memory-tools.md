# ADR-0015: MCP инструменты для персистентной памяти агентов

**Статус:** accepted
**Дата:** 2026-05-29
**Автор:** Александр Мельник

---

## Контекст

Memex нужно интегрировать с AI-агентами Hermes и OpenClaw как персистентная долгосрочная память. Агентам нужно:
- сохранять произвольный текст (не только файлы)
- находить релевантные воспоминания по смыслу
- удалять устаревшие записи
- классифицировать память тегами

Существующий MCP сервер (`src/mcp/server.py`) имел только два инструмента: `add_document` (только файл) и `query` (LLM-синтез без альтернатив). Этого недостаточно для агентного сценария.

Deployment plan: Фаза 1 — одна машина, docker-compose. Фаза 2 — Memex на отдельном сервере (см. ADR-0016 когда будет).

## Рассматриваемые варианты

### Вариант 1: Один универсальный инструмент `memory(action, ...)`

Все операции через один инструмент с параметром `action: remember|recall|forget|...`.

**Плюсы:** меньше инструментов в списке.
**Минусы:** LLM сложнее выбирать action; хуже tool descriptions; хуже observability (всё под одним именем).

### Вариант 2: Шесть специализированных инструментов (выбранный)

Каждая операция — отдельный инструмент с чётким описанием и schema.

**Плюсы:**
- LLM легче выбрать нужный инструмент по имени и описанию
- Каждый инструмент имеет минимальный набор параметров
- Проще логировать и отлаживать
**Минусы:**
- Больше инструментов в `list_tools` (LLM видит 6 вместо 1)

### Вариант 3: Прямой доступ к БД (без HTTP)

MCP сервер обращается к PostgreSQL и embeddings напрямую, минуя FastAPI.

**Плюсы:** нет зависимости от запущенного веб-сервера.
**Минусы:** дублирование всей логики retrieval pipeline; два места поддержки.
**Отклонён:** в Фазе 1 агенты всегда работают рядом с Memex.

## Решение

Выбираем **вариант 2** — шесть специализированных инструментов поверх HTTP API.

## Инструменты

| Инструмент | Sync/Async | Описание |
|---|---|---|
| `remember(content, title?, tags?)` | async | Сохранить текст; возвращает `job_id` |
| `recall(query, raw?, top_k?)` | sync | `raw=false` → LLM-ответ; `raw=true` → сырые чанки |
| `index_file(path, tags?)` | async | Проиндексировать файл с диска |
| `check_indexing(job_id)` | sync | Статус индексации; при первом `done` сохраняет title/tags |
| `list_memories()` | sync | Список документов с тегами и датами |
| `forget(doc_id)` | sync | Удалить документ из БД и с диска |

## Ключевые решения

**Async индексация.** `remember` и `index_file` возвращают `job_id` немедленно — агент сам решает когда проверить готовность через `check_indexing`. Fire-and-forget или polling — на усмотрение агента.

**Теги через `metadata_` JSONB.** Document модель уже имеет JSONB поле `metadata_`. Теги хранятся как `{"tags": ["meeting", "client"]}`. Нет миграции схемы. Фильтрация по тегам в поиске — вне скоупа v1 (теги для организации и `list_memories`).

**Отложенное применение title/tags.** Т.к. Document создаётся воркером асинхронно, title и tags кешируются в памяти MCP сервера под `job_id`. При первом вызове `check_indexing` со статусом `done` сервер вызывает `PATCH /api/documents/{doc_id}` для применения. Кеш in-memory — приемлемо для Фазы 1 (одна машина, один процесс). В Фазе 2 (remote) потребует persistence.

**`recall(raw=true)` без LLM.** Новый endpoint `POST /api/search/chunks` запускает retrieval pipeline (semantic + BM25 + reranker) и возвращает top-K чанков без LLM-вызова. Агент сам решает что делать с контекстом — дешевле и быстрее при высокой частоте запросов.

**Транспорт.** stdio (стандарт MCP для локального deployment). При переходе на Фазу 2 потребуется HTTP/SSE транспорт — отдельный ADR.

## Новые API endpoints

| Метод | Путь | Описание |
|---|---|---|
| `DELETE` | `/api/documents/{doc_id}` | Удалить документ + файл с диска |
| `PATCH` | `/api/documents/{doc_id}` | Обновить title и metadata (tags) |
| `POST` | `/api/search/chunks` | Сырой retrieval без LLM синтеза |
