# ADR-0014: Streaming-ответ LLM через SSE

**Статус:** proposed
**Дата:** 2026-05-29
**Автор:** Александр Мельник

---

## Контекст

Сейчас поиск работает синхронно: пользователь отправляет вопрос, ждёт 5–15 секунд пока отработает весь pipeline (retrieval → reranker → LLM), и только потом видит ответ целиком. При длинных ответах (анализ резюме, большие документы) это заметно.

Хотим показывать токены по мере генерации, чтобы пользователь начинал читать сразу.

## Рассматриваемые варианты

### Вариант 1: Оставить синхронный подход

**Как работает:** текущее поведение — полный ответ после завершения pipeline.
**Плюсы:**
- Нет изменений в архитектуре
- HTMX-подход единообразен на всех страницах
**Минусы:**
- Ощутимая пауза 5–15с перед первым токеном
- Плохо масштабируется с ростом документов и длины ответов
**Риски:**
- UX деградирует при больших базах знаний

### Вариант 2: SSE + fetch API (выбранный)

**Как работает:** новый endpoint `POST /search/stream` возвращает `StreamingResponse` (`text/event-stream`). Фронтенд заменяет HTMX-форму поиска на ручной `fetch` + `ReadableStream`. Токены добавляются в бабл по мере поступления. Источники приходят отдельным SSE-событием после последнего токена.

**Протокол событий:**
```
event: token
data: "Алек"

event: token
data: "сандр"

event: sources
data: [{"doc_id": "...", "filename": "resume.pdf", "page": 1}]

event: done
data: {}

event: error
data: {"message": "..."}
```

**Плюсы:**
- Первый токен через ~0.5–2с (retrieval всё равно блокирует до старта стрима)
- Пользователь читает пока LLM ещё генерирует
**Минусы:**
- Поиск выбивается из HTMX-паттерна (fetch-островок в HTMX-приложении)
- Тестирование streaming endpoint сложнее
**Риски:**
- Локализованы в одном компоненте (`index.html` + `/search/stream`)

### Вариант 3: HTMX SSE-расширение

**Как работает:** `hx-ext="sse"` + `EventSource`.
**Плюсы:** остаётся в HTMX-парадигме.
**Минусы:** SSE-расширение HTMX ориентировано на push-уведомления (GET + EventSource), не на request-response стрим. Для POST-запроса с параметрами подходит плохо — нужны workaround'ы.
**Риски:** хрупкое решение, плохо документированный паттерн.

## Решение

Выбираем **вариант 2** (SSE + fetch API) когда будем реализовывать.

Retrieval pipeline (семантический поиск + BM25 + reranker) выполняется до начала стрима — это неизбежно, т.к. источники нужны как контекст для LLM. Реальный выигрыш — время генерации LLM, не полного pipeline. Для коротких ответов (<100 токенов) разница незначительна; для длинных (>300 токенов) — ощутима.

Несогласованность с HTMX приемлема: один компонент из трёх страниц, логика изолирована в `index.html`.

## Обработка ошибок

При любой ошибке (сеть, LLM API, таймаут) — **очищаем бабл и показываем сообщение:**

```
⚠ Не удалось получить ответ. Попробуй ещё раз.
```

Частичный контент не сохраняем — он вводит в заблуждение (пользователь не знает, на каком слове оборвалось). Технически: `AbortController` для таймаута, `try/catch` на `reader.read()`, `event: error` от сервера.

## Изменения при реализации

**Backend:**
- Добавить `complete_stream() -> AsyncIterator[str]` в `LLMProvider` протокол
- Реализовать в `OpenAIProvider` и `ClaudeProvider`
- Новый endpoint `POST /search/stream` → `StreamingResponse`

**Frontend:**
- `templates/index.html`: заменить HTMX-форму на `fetch` + `ReadableStream`
- Inject пустой bot-бабл сразу, дописывать токены, добавить source tags по событию `sources`

**Затрагиваемые файлы:** `src/llm/protocol.py`, `src/llm/openai_provider.py`, `src/llm/claude.py`, `src/ui/pages.py`, `templates/index.html`
