# ADR-0003: Retrieval Strategy — Hybrid Search (Semantic + BM25 + RRF)

**Статус:** accepted
**Дата:** 2026-05-29
**Автор:** Александр Мельник

---

## Контекст

Нужно находить релевантные чанки по пользовательскому запросу. Приоритет: recall первичен — лучше найти лишнее, чем пропустить нужное. Корпус смешанный: личные заметки, статьи, технические PDF. Запросы разные: от семантических ("расскажи про архитектуру") до точных ("GIN индекс JSONB").

## Рассматриваемые варианты

### Вариант 1: Только Semantic Search (pgvector)

Embedding запроса → cosine similarity → top-K чанков.

**Как работает:** один индекс, один запрос.
**Плюсы:**
- Простейшая реализация
- Хорошо на семантических, концептуальных запросах
- Кросс-языковой поиск из коробки
**Минусы:**
- Плохой recall на точных терминах, аббревиатурах, именах файлов
- "GIN индекс" может не найти чанк где написано "GIN" если embedding "размыт" соседними токенами
**Риски:**
- Для технических заметок с терминологией — существенные пропуски

### Вариант 2: Только BM25 (Full-text search)

Инвертированный индекс по словам, ранжирование по BM25 формуле.

**Как работает:** ищет точные слова и их морфологические формы.
**Плюсы:**
- Точный recall по конкретным терминам
- Быстрый, детерминированный
**Минусы:**
- Не понимает смысл: "ускорение запросов" ≠ "оптимизация производительности"
- Нет кросс-языкового поиска
- Синонимы, перефразирования — пропускает
**Риски:**
- Семантические запросы дают плохой recall

### Вариант 3: Hybrid Search (Semantic + BM25 + RRF)

Параллельно: semantic top-K и BM25 top-K → объединение через Reciprocal Rank Fusion.

**Как работает:** два независимых поиска по одним и тем же L1 чанкам, слияние по позиции в ранжированных списках (формула 1/(rank+60)).
**Плюсы:**
- Semantic ловит смысловые запросы, BM25 ловит точные термины — вместе покрывают оба случая
- Чанк попавший в оба списка достоверно релевантен (два независимых голоса)
- RRF не требует нормализации шкал — работает только с позициями
- BM25 не требует доп. инфраструктуры: PostgreSQL tsvector встроен
**Минусы:**
- Два индекса (pgvector + tsvector) вместо одного
- Два параллельных запроса к БД
**Риски:**
- Если BM25 возвращает 0 результатов (семантический запрос) — RRF работает только на semantic. Это нормальное поведение.

## Решение

Выбрал **Вариант 3: Hybrid Search с RRF**.

Recall — приоритет. Semantic и BM25 имеют разные слепые зоны: semantic пропускает точные термины, BM25 пропускает синонимы и смысловые запросы. Hybrid закрывает оба случая. RRF — простой и эффективный способ слияния без тюнинга весов. PostgreSQL tsvector уже есть в стеке (не нужен Elasticsearch), overhead минимален. На корпусе < 1000 документов два параллельных запроса — миллисекунды.

**BM25 backend:** PostgreSQL tsvector (встроен, один бэкенд для всего). Точная Okapi BM25 формула (rank_bm25) — потенциальное улучшение в будущем, если recall окажется недостаточным.

**RRF параметр k=60** — стандарт из оригинальной paper, работает хорошо без тюнинга на малых корпусах.

## Последствия

**Придётся:**
- Добавить `content_vector VECTOR(1536)` в chunks (только L1)
- Добавить `tsv TSVECTOR GENERATED` в chunks (L1 и L2)
- Реализовать `RRFMerger` с дедупликацией по chunk id
- Запускать два параллельных запроса при каждом поиске

**Стало проще:**
- Recall существенно выше чем при одном методе
- Слепые зоны одного метода компенсируются другим
- Нет новой инфраструктуры: всё в PostgreSQL

**Путь к улучшению:** если recall всё равно недостаточен — добавить Query Decomposition (вопрос → N подвопросов → параллельный поиск) поверх этого же pipeline без изменения индексов.
