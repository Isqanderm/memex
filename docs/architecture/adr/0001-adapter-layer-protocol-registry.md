# ADR-0001: Adapter Layer — Protocol-based Registry

**Статус:** accepted
**Дата:** 2026-05-29
**Автор:** Александр Мельник

---

## Контекст

Система должна принимать документы разных форматов: PDF, DOCX, TXT, Markdown — и в будущем потенциально URL, Telegram, email. Нужно выбрать архитектуру слоя обработки входящих данных.

Ограничения:
- Личный проект, один разработчик
- Форматы добавляются постепенно, начиная с файлов
- Каждый адаптер должен возвращать единообразную структуру для downstream pipeline

## Рассматриваемые варианты

### Вариант 1: Простой реестр функций

```python
ADAPTERS = {".pdf": parse_pdf, ".md": parse_markdown}
```

**Как работает:** dict по расширению файла, вызываем нужную функцию.
**Плюсы:**
- Минимум кода
- Добавить адаптер = одна строка
**Минусы:**
- Нет типобезопасности на выходе
- can_handle только по расширению — нельзя проверить magic bytes
- Нет метаданных на выходе — адаптер возвращает сырой текст
**Риски:**
- При росте форматов теряется контроль над контрактом выхода

### Вариант 2: Protocol-based Registry

Адаптер — класс с методами `can_handle(source) → bool` и `parse(source) → ParsedDocument`. Реестр итерирует адаптеры и вызывает `can_handle`.

**Как работает:** typed интерфейс, каждый адаптер сам решает умеет ли он обработать источник.
**Плюсы:**
- Единый типизированный контракт на выходе (`ParsedDocument` с секциями и метаданными)
- `can_handle` может проверять magic bytes, MIME type, не только расширение
- Легко тестировать в изоляции
- Добавить новый тип источника (URL, stream) — новый класс, ядро не меняется
**Минусы:**
- Чуть больше boilerplate чем dict
**Риски:**
- Порядок регистрации важен (первый подходящий wins) — нужно документировать

### Вариант 3: External plugins via entry_points

Адаптеры — отдельные pip-пакеты с autodiscovery через `importlib.metadata`.

**Как работает:** `pip install memex-notion` → адаптер автоматически обнаруживается.
**Плюсы:**
- Независимое версионирование адаптеров
- Третьи лица могут писать адаптеры
**Минусы:**
- Значительный overhead для личного проекта
- Контракт `ParsedDocument` должен быть стабильным API — сложная ответственность
- Сложная отладка
**Риски:**
- Preoptimization: экосистемы нет и не предвидится

## Решение

Выбрал **Вариант 2: Protocol-based Registry**.

Для личного проекта с 5-10 форматами документов это правильный уровень абстракции. Главное — контракт на выходе: адаптер возвращает `ParsedDocument` со структурой секций, а не сырой текст. Это позволяет Chunker'у принимать умные решения о границах чанков, опираясь на структуру документа (заголовки, уровни). Вариант 1 теряет эту структуру. Вариант 3 избыточен без реальной экосистемы.

## Последствия

**Придётся:**
- Реализовать `DocumentAdapter` Protocol и `AdapterRegistry`
- Каждый новый формат = новый класс с `can_handle` + `parse`
- Документировать порядок регистрации адаптеров

**Стало проще:**
- Тестирование адаптеров изолированно с фейковым Source
- Добавление поддержки URL/stream без изменения ядра
- Типобезопасная передача структуры документа в Chunker

**Стало невозможным:**
- Быстро добавить адаптер одной строкой (нужен класс)

**Путь к Варианту 3:** если появится потребность в публичной экосистеме — Protocol интерфейс остаётся тем же, добавляется только autodiscovery слой поверх.
