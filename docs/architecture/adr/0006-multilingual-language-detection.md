# ADR-0006: Мультиязычность — Language Detection per Chunk

**Статус:** accepted
**Дата:** 2026-05-29
**Автор:** Александр Мельник

---

## Контекст

Личный корпус содержит документы на разных языках — минимум RU и EN, возможно другие. Это создаёт проблему для BM25 (tsvector): PostgreSQL использует языковые словари для стемминга, и конфиг языка должен совпадать с языком текста. Неправильный конфиг — плохой recall.

Semantic search (OpenAI embeddings) мультиязычен из коробки и не требует специальной обработки.

Дополнительный кейс: один документ может содержать текст на нескольких языках (EN технический текст + RU комментарии).

## Рассматриваемые варианты

### Вариант 1: Фиксированный язык 'simple'

Использовать PostgreSQL конфиг 'simple' для всех документов — без стемминга, только lowercase.

**Как работает:** `to_tsvector('simple', content)` для всех чанков.
**Плюсы:**
- Нулевая сложность
- Работает для любого языка
**Минусы:**
- Нет стемминга: "индексирование" и "индекс" — разные токены, BM25 их не связывает
- Существенно хуже recall по морфологическим формам слов (особенно критично для RU)
**Риски:**
- Recall BM25 на RU тексте значительно деградирует

### Вариант 2: Language Detection на уровне документа

Определять язык один раз при парсинге документа, использовать для всех его чанков.

**Как работает:** `langdetect` или `lingua-py` на полном тексте документа → язык сохраняется в `documents.language`.
**Плюсы:**
- Простая реализация
- Один вызов detection на документ
**Минусы:**
- Смешанные документы (EN статья с RU комментариями) — неправильный язык для части чанков
**Риски:**
- Технические документы с EN терминами + RU текстом — частый случай для личного корпуса

### Вариант 3: Language Detection на уровне чанка

Определять язык для каждого L1 чанка отдельно при индексации.

**Как работает:** `langdetect` на `chunk.content` → `chunk.language` → `to_tsvector(lang_config, content)`.
**Плюсы:**
- Точная обработка смешанных документов
- BM25 всегда использует правильный стемминг
- При поиске: определяем язык запроса → используем тот же конфиг
**Минусы:**
- Вызов detection на каждый чанк при индексации (~1000 чанков = 1000 вызовов, но быстрых)
- `langdetect` ненадёжен на коротких текстах (< 50 токенов) → fallback на 'simple'
**Риски:**
- Короткий чанк может быть определён неправильно → fallback 'simple' покрывает это

## Решение

Выбрал **Вариант 3: Language Detection на уровне чанка**.

Корпус содержит технические тексты где смешение EN/RU внутри одного документа — норма. Правильный стемминг критичен для RU морфологии (у русского языка богатая флексия). `langdetect` быстрый (~1ms на чанк), накладных расходов практически нет. Fallback на 'simple' для коротких или неопределённых чанков защищает от ошибок detection.

Маппинг языков:
```
'ru' → 'russian'
'en' → 'english'
'de' → 'german'
 *   → 'simple'   ← fallback
```

## Последствия

**Придётся:**
- Добавить `language TEXT` поле в chunks
- Добавить шаг `LanguageDetector` в Ingestion Pipeline (между Chunker и IndexingStage)
- `tsv TSVECTOR` — теперь не GENERATED ALWAYS (язык переменный), вычислять в коде при INSERT
- При поиске: определять язык запроса и использовать правильный `plainto_tsquery` конфиг

**Стало проще:**
- BM25 recall на RU текстах существенно выше
- Система прозрачно работает с любым языком без ручной конфигурации

**Известные ограничения:**
- Чанки < 50 токенов — detection ненадёжен, используем 'simple'
- Языки без PostgreSQL словаря (например, японский) → fallback 'simple'
